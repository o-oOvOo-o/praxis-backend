# Thread switch performance investigation

The policy probe extracts the production `ThreadViewCache` implementation and substitutes only widget payloads and thread IDs. Run `python scripts/benchmark-thread-view-cache.py` from praxis-rs. It checks eviction, take/drain accounting, and entry limits, then exercises cyclic working sets. It does not measure transcript replay, input restoration, terminal frames, memory consumption, or real conversation latency.

On 2026-09-07 the old 400-cell shared budget retained only one long cached view. Cycling three threads of 250 or 1000 cells produced 0 hits in 10,000 switches. Reserving two recent cached views produced 9,998 hits, with two compulsory misses. Two-thread and eight-short-thread cases retained their prior hit counts. This trades retention of one additional long view for eliminating that replay cycle; the number-of-entries limit remains eight. The cell budget is soft for the two protected views, so retained bytes still need measurement with real conversations.

Eight long threads and sixteen-thread working sets still thrash. Full TUI first-frame latency, live background catchup, composer restoration, memory accounting, and long-history rendering remain unverified and are required before claiming the thread-switch goal complete. Existing binaries predate these edits and cannot validate them.

## Live frame measurements

`praxis_tui::thread_switch` emits `thread switch frame committed` after a successful `tui.draw`. `elapsed_us` measures from entry to the switch path, and `draw_us` measures that terminal draw. `first_frame=true` identifies the first matching active-thread frame. `ready=true` additionally requires no replay buffer, a materialized view revision, and no pending cached-view catchup. This is UI readiness, not proof that every future backend event has arrived. Failed draws produce no successful frame sample; frames for another active thread do not complete the sample. A superseding switch replaces the pending measurement.

The measurement state machine has two passing standalone tests for wrong-thread rejection, provisional versus ready frames, and a hot first frame that is already ready. Source integration is not yet compiled into a fresh executable because the shared build drive has less than 1 GB free. Existing binaries cannot supply measurements for this instrumentation. The pending acceptance scope remains real TUI conversation switching, first-frame and ready-frame distributions, live-event/input fidelity, and memory measurements across larger working sets.

## Stable working-set probe

The 12-click old-binary experiment produced seven distinct viewport-body snapshots and RSS samples from 130 to 312 MiB, but revisiting a row did not revisit the same thread because the list reordered. It is navigation evidence only, not an eight-thread cyclic latency baseline.

Debug builds now support `PRAXIS_TUI_THREAD_SWITCH_PROBE` pointing to a JSON array of thread UUIDs. After the startup thread has rendered and workspace rows have loaded, the probe queues a debug-only event that resolves the target row and invokes `resume_session_target`, the same path used by sidebar clicks. It queues each subsequent UUID only after the prior thread emits its ready-frame event. This avoids composer input and bypasses only unstable screen-coordinate selection, while preserving workspace configuration recovery, attachment, replay, and rendering. Targets absent from the loaded rows fail explicitly. Workspace timing starts before configuration recovery; the nested cached-view attempt no longer resets it. Release builds omit this diagnostic entry point. A stalled/failed switch stops plan progression and is not silently counted as success.

The terminal driver accepts `--thread-plan PATH`, saves decoded terminal screens using pyte, and validates exact ready-frame UUID order plus the final completion marker. Failed validation exits with code 2 after saving evidence. Three report tests cover missing data, first/ready separation, and plan ordering/completion. The selected local working set contains eight native threads with 84, 65, 81, 73, 20, 28, 91, and 140 turns, repeated four times; the private IDs and plan remain in `.local/praxis-quality`. The plan has not run against a new binary yet because the canonical target is still held by the root app build.

The queued build subsequently acquired the target lock but failed while building `praxis-api` and `praxis-otel` with OS error 112 (disk full). No new TUI executable was produced. Only object files from these two failed compilation units were removed; the fixed-UUID run remains pending. The harness now samples process RSS every 100 ms independently of mouse actions, so UUID-plan runs also contain memory evidence. It rejects an existing application-log directory before launching and clears an inherited probe environment variable unless `--thread-plan` is explicitly supplied, preventing stale-log acceptance and accidental probe activation. Three report tests, Python syntax checks, and the diff whitespace check pass after this correction.

Removing eight August-only generated Praxis runtime/gateway libraries subsequently restored approximately 15 GB for the canonical target; the same TUI build command is running again. The removal manifest and retry log are under `.local/praxis-quality`. Reports now separate ready-frame distributions into cache hits, misses, and unknown outcomes, with four passing parser/report tests. `thread replay projected` logs the synchronous replay stage duration, turn/event counts, and generated cell count so the real run can distinguish projection cost from drawing. These changes supply diagnostics; they do not establish a performance improvement or functional acceptance.

The retry compiled the core, gateway, and TUI libraries, including the workspace-path probe correction, but failed linking the TUI binary with LNK1318 / PDB `LIMIT (12)`. The failed PDB was removed. A targeted `cargo rustc -p praxis-tui --bin praxis-tui -j 2 -- -C link-arg=/DEBUG:NONE` is queued on the same canonical target. This disables only final-link symbols for the diagnostic executable, retains debug assertions and the probe entry point, and does not change dependency profiles. Real latency and functional acceptance still require that executable to finish linking and run.

## First real fixed-UUID runs

The targeted link succeeded. `pty-fixed-eight-current` ran the fresh executable (SHA-256 `7e216ad53516c951794af4a59dfa97d30636f18c6f62d4e0793de60b09501fbe`) for 60 seconds. The first cold target exceeded `INTERACTIVE_THREAD_ATTACH_TIMEOUT` (5 seconds); the terminal displayed the attach timeout and the plan correctly failed with zero ready frames. The process exited, with no harness reader errors; 598 RSS samples peaked at 329.2 MiB and ended at 152.3 MiB. This is a failed cold-open test, not a successful switch benchmark.

A second executable added gateway phase timings and ran in `pty-fixed-eight-stages`. The same cold target reached history-loaded at 3,430,130 us, config-loaded at 3,436,613 us, session-resumed at 6,363,096 us, and response-ready at 6,432,086 us. The response arrived after the TUI deadline, so this run also produced zero ready frames. History loading and session restoration dominate this sample; configuration loading and response projection are comparatively small. Next investigate the native history fold and session restore path before claiming that cache or render changes address this cold-open failure. No timeout increase or fallback has been applied to hide it.

The read-only `praxis-thread-store-journal` example `read_snapshot <root> <thread-id>` isolates journal validation and event decoding. The same 17,750-event thread took 2,841,946 / 2,830,865 / 2,793,918 us before buffering (`journal-read-baseline.log`). Sequential segment recovery now uses `BufReader<File>` instead of separate OS reads for each frame header and payload. CRC, continuity, and committed-prefix checks remain in the same loop; writer-only tail repair uses the underlying file and exits the scan immediately. A regression covers ordered replay across multiple read buffers, read-only preservation of an incomplete tail, and writer tail repair. The journal test command is still waiting on the shared target (its pre-existing filename `journal-tests-before.log` will contain the buffered-source tests, not a baseline test run). Post-change journal timings and real TUI timings remain required before retaining this as a demonstrated optimization.

Source inspection confirms two separate full journal recovery paths during cold resume: `ThreadHistoryReader::read_initial_history` uses `ThreadStore::fold_thread_events` / `consume_snapshot`; subsequent `NativeRolloutWriter` initialization calls `ThreadStore::open_thread`, which recovers again through `ThreadJournal::open_and_fold`. Their similar measured durations are consistent with this duplicate work. Eliminating it requires ownership of one recovered writer plus its folded history across configuration/session initialization, rather than skipping validation or treating file metadata as proof of journal integrity. The current change only buffers reads; it does not yet eliminate the second recovery.

The buffer experiment was subsequently rejected and reverted. After correcting the test fixture to keep the partial tail in the final segment, 20 journal tests passed; one unchanged pre-existing source-string assertion (`stored_batch_exposes_only_consuming_event_projection`) was explicitly filtered after failing in the full run. Two compiled reader variants were run in buffered/unbuffered/unbuffered/buffered order against the same thread, three scans per invocation. All 12 scans returned 17,750 events. Median scan time was 3,185,370 us unbuffered versus 3,564,547 us buffered (`journal-buffering-ab.json`); concurrent build load makes this a noisy comparison, but it does not justify retaining buffering. `recovery.rs` is restored to its original implementation. The ordered replay/tail-repair regression and read-only example remain useful for the recovery consolidation work; no performance improvement is claimed from this experiment.

Recovery consolidation is now being implemented at the rollout ownership boundary. `PreparedRolloutResume` uses `ThreadStore::open_thread_and_fold` to decode native rollout items while recovering and retaining the writer. Its non-cloneable `PreparedRolloutWriter` validates the path when consumed. Existing writer metadata/locator reconciliation is shared through `NativeRolloutWriter::from_recovered`. Tests cover retained exclusive ownership, appending after transfer, release on drop, and rejecting a different path. Their command is queued in `prepared-resume-tests.log`; final unbuffered journal tests are separately queued in `journal-tests-final.log`. The new preparation API is not yet wired through ThreadManager and session startup, so the real cold-resume path still performs two recovery passes and no new latency improvement is established.

The prepared writer is now wired through gateway cold resume, ThreadManager, the spawn request, session startup artifacts, and `RolloutRecorder::new_with_prepared_writer`. The native route transfers the existing writer instead of opening it again; legacy/history-supplied and new-thread routes carry no prepared writer. The gateway's history-loaded marker includes `prepared_writer` because that stage now includes writer recovery. Existing metadata/locator repair can still require additional reads for old or missing projections. A third regression creates the recorder while the prepared writer retains its lock, verifying that ownership is transferred instead of reopened. Compilation (`prepared-resume-typecheck.log`) and the three storage/recorder tests remain queued behind the root build. End-to-end TUI latency and behavior are still unverified for this change.
